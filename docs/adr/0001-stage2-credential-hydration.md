# Stage 2 rehydrates the profile's `.env` inside the Cron script child

A Cron pre-run script is spawned through a sanitized child environment that strips every declared provider credential. The proactive bridge therefore runs Stage 2 with no key in `os.environ`, so a `config.yaml` main-model key written as `${VAR}` expands to nothing, stays a 39-character literal placeholder, and is sent to the provider as an invalid key — every worker dies with an authentication error that says nothing about the real cause. We fixed this by having the bridge call the host's `load_hermes_dotenv(hermes_home=home)` on entry, exactly as the Cron main-agent process already does, and by making Stage 2 raise on a still-unexpanded `${VAR}` reference while naming the variable.

Considered and rejected: (a) reading only `<home>/.env` with a private parser — cheap, but it forks the host's layered credential semantics (`.op.env`, external secret sources, managed env) into a second implementation that would silently drift; (b) relaxing the child-environment scrub for this script — impossible without touching the Hermes core repository, and the scrub is a deliberate boundary that must not be widened for one consumer; (c) letting Stage 1 short-circuit on the unresolved key — it would report a broken key on quiet runs that never needed one, turning a real alert into nightly noise.

Consequences: the bridge child now holds the profile's credentials in its own environment for the length of the run, which is why the hydration lives behind one named function rather than scattered imports; and a Stage 3 / in-process tick path never touches it, because those already run with the host's environment hydrated.
